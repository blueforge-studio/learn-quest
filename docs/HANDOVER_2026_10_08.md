## How things work (learned today)

- **books-platform deploys**: a merge to `main` fires a webhook project deploy of all 10 containers (~25 min on a busy fleet). Don't also run `forge app-deploy` per app — it collides and risks the documented host-port/override trap. The control-plane record (`forge deployments show <id>`) can stay "building" and `api.blueforge.studio` can 502 mid-deploy; confirm with `ssh root@178.104.130.80 docker ps` (container ages) and the smoke harness. `app-1` has no DNS/ssh alias on this machine; its address is in `forge-control/infrastructure/fleet/fleet.yml` (178.104.130.80). CLAUDE.md in books-platform still says "forge-app-2" — same box.
- **Content lives in the repo AND in object storage.** Source: `apps/*/public/data/books/<locale>/<book>/scenes/**` (adventure scenes are nested per chapter; a scene's id is its `id` field, not its filename — 138 files differ). Production serves object storage via books-api, so repo fixes change nothing live until uploaded with `scripts/upload-book-content.ts --bookId --type --locale --booksDir` and `BOOKS_API_KEY` (= the container's `INTERNAL_API_KEY`). **Build the upload dir from the LIVE API JSON when production differs from the repo** (it did: short vs expanded text) so only intended fields change; verify by reading back from the API.
- **Reader contracts that bit us**: books-api `GET /api/content/:book?chapter=N` returns a BARE ARRAY (client now accepts array or `{scenes}`); story `nextScenes[]` are followed by `.id ?? .sceneId`; `QuizRunner` `autoAdvance={false}` never calls `onComplete` — use the new `onAnswer`; adventure chapters are entered by PROGRESSION (all scenes visited -> chapterComplete -> CONTINUE), not by edges.
- **Tests can lie via mocks**: interactive-book's `setup.tsx` mocked `QuizRunner` to call `onComplete` on every click and ignore `correctAnswer`, so the dead-end bug was invisible. The mock now mirrors the real component. For every fix, run the new tests against the unfixed code (stash the source change) to prove they fail.
- **Link guard**: `pnpm content:check` (`scripts/check-book-content.mjs`) checks `nextScenes[].id|sceneId`, `choices[].nextSceneId|outcome.target`, `onCorrect/onIncorrect` (also under `comprehensionCheck`), `outcomes[].sceneId`, `success/failure(Outcome).sceneId`, `skillCheck.outcomes[].sceneId`. It runs in `.gitea/workflows/ci.yml` (the `.gitea` dir is the one that runs). Baseline = ratchet.
- **Docs repo (`learn-quest`) main is protected**: push a branch, open a PR with the Gitea API (`~/.forge-secrets/forge-git-token`, org `blueforge-studio`), merge only when the user says so.

## On-host upload recipe (worked 2026-10-08; avoids extracting the admin key)
Build the upload dir from the LIVE scene JSON (change only the intended fields), `COPYFILE_DISABLE=1 tar czf - … | ssh root@<app-1> "mkdir -p $D && tar xzf - -C $D; find $D -name '._*' -delete"`, then run a SEPARATE `ssh root@<app-1> bash -s < script` that reads `INTERNAL_API_KEY` from `/opt/books-platform/books-api.env` inside the remote shell and POSTs `{type, locale, files:[{key, base64, contentType}]}` to `/api/admin/<book>/content` (key = path relative to the book dir). Don't combine a piped tar and a heredoc on one ssh (stdin collision: nothing runs). macOS tar adds `._*` files — delete them or they get uploaded. Always read back from `/api/content/...?cb=<x>` and run the live content check afterwards.

## Traps

- **pnpm 11 `minimumReleaseAge` (1 day)**: `pnpm update` silently skips versions <24h old (it can even re-resolve older ones). Right after a publish use `pnpm add pkg@<exact>` (adds `minimumReleaseAgeExclude`), or wait.
- **A lockfile keeps old TRANSITIVE resolutions**: bumping `web-app` alone left `lang-lesson-types@0.2.3` -> `lesson-framework@0.1.5` in the tree (a second copy, anchors missing). `game-features`/`web-app` use caret ranges, NOT exact pins — I misdiagnosed this at first. Check `pnpm why @learnquest/lesson-framework`.
- **Production secrets**: reading a secret out of a running production container is blocked for me by the permission classifier (twice: bulk worktree removal also). Don't work around it: prepare the command and have the operator run it with `!`. Read-only `docker ps/logs` on app-1 is fine.
- **Cross-session**: peer messages carry no user authority. (forge-control first believed its token got 403 on books-platform issue comments; it was their Python client's user-agent being rejected, not a permission limit. They have posted their own fix summary on #55.) forge-control's earlier #55 comment handed the next step to "the books-platform owner" — it ended up being fixed by them after the operator authorised it.
- Credential status tool: `forge service credentials status postgres --project books-platform --host app-1` said "everything agrees" while books-api was being rejected; in-container / certain-path logins can pass for the wrong reason. Test with a deliberately wrong password to see whether a path actually checks passwords.
- zsh: quote globs (`-g '*.tsx'`), `echo =====` fails (`=` expansion), `sleep` loops >~9 min get moved to the background (use bounded polls or the completion notification).
- `validate-adventure-book.ts` prints `0 errors` even when the book directory is not found; its `BOOKS_DIR` is joined onto the cwd (use a path relative to `scripts/`).
- Background task notifications are automatic events, not user messages.
