  image (18 on app-3, ~15 GB). Instead: dangling prune (684 MB) + `docker rmi` by tag of unused

## app-3: what fills `/` — found (read-only; nothing deleted)

**`/var/lib/containerd.pre-bind` = 110 GB (99 GB snapshotter + 10.8 GB content)** of the 121 GB used on `/`.
It is the original containerd root left on sda1 when containerd was moved to `/dev/sdb` via a
bind mount (`/etc/fstab`: `/var/lib/docker/forge-containerd /var/lib/containerd none bind,nofail,…`).
Verified orphaned: not mounted (0 entries in `/proc/mounts`), 0 open files, containerd (PID
2208691) runs on the bind-mounted `/var/lib/containerd`, whose Docker root is on sdb (19% used).
Dir mtime 2026-08-17 (migration date); the content dir was last touched 2026-09-30.

- Deleting it would take `/` from ~84% to roughly 10%. **Not done — irreversible, and it is the only
  pre-migration copy of containerd state.** Needs operator OK. Checked app-1/2/4: **none has a
  `containerd.pre-bind`**; app-1/2 have no separate containerd mount, so their 80–82% on `/` is real
  (images live on `/` there — prune is meaningful), and app-4's 7% is its `/dev/sdb` containerd mount.
- Caveat: fstab uses `nofail`. If the bind ever failed at boot, containerd would start on an empty
  sda1 dir, not on `.pre-bind`, so `.pre-bind` is not a silent fallback.
- Unhealthy containers (both pre-existing): `clinic-os-api-1-1` — **false alarm**, healthcheck GETs
  `/` which 404s (app serves fine; fix the check path in clinic-os). `forge-auth-auth-1-1` —
  `/api/health` 503 inside the container, but public `forge-auth.blueforge.studio` is 200/`db: ok`
  with ~1.5 d uptime vs the container's 5 d → likely a stale instance not serving traffic. Left
  untouched; confirm which instance the proxy routes to before removing.
