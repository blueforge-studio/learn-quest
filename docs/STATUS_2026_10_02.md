## The blocker, and what fixed it

```
platform-api: the image build context at /tmp/forge-builds/<id>/services/platform-api
contains 25 symlinks that will not resolve inside the image
```

The guard is right. `COPY` carries symlinks verbatim, so the image would build and then fail at
runtime (`ERR_MODULE_NOT_FOUND`, or sharp's native addon failing to load) — which is exactly
what happened on 2026-09-29 (51-minute crash loop).

`resolveStageRoot` (`packages/build-worker/src/stages/deploy/build-context.ts`) has a
documented escape hatch: a workspace member with a **committed Dockerfile** *and* a non-empty
`workspaceDependencyClosure` stages the repo root and returns `flat: false` — and the guard is
only passed when `stage.flat` is true. platform-api's closure is 11 workspace packages, so the
condition holds. Precedent: roomcraft's api, 2026-09-16.

`resolveUserDockerfile` then picks the committed file up and skips the template, so
`assertDockerfilesConsistent` diffs the file against itself and passes.

## The forge-control defect (option 1) — PARKED, findings recorded

**I could not isolate it to a line.** I ruled out several hypotheses; the remaining gap is
narrow and stated here so the next session does not re-walk it.

Confirmed working, in the deployed worker dist (`ci-1`, `forge-build-worker`):

- `hono-api.js:174` `replaceWithDereferencedCopy(hoistDir)` → `:182`
  `assertSelfContainedContext(ctx.appPath, …)` — correct order, matches repo source.
- The dereference genuinely works on that Node (v22.23.3). I ran the **real** exported
  functions against a farm built to match the failing shape exactly (pnpm store at the root, a
  2-deep member, a workspace sibling with its own `node_modules`):
  `assertSelfContainedContext` threw on 3 symlinks → `replaceWithDereferencedCopy` OK →
  guard passed, 0 symlinks left, all three entries real dirs. **The code is correct.**

Therefore `replaceWithDereferencedCopy` was simply **never called** for that directory in the
failing run. The error was *bare* — not wrapped in `build failed for app 'platform-api' …`,
which `generator-build.ts:136` would have added — so `hono-api.build()` did not throw, and
either it did not run, or it ran and the farm was re-created afterwards.

Facts that constrain it:

- The `build` stage took **228 s** (and 292 s on a second trace) — that is a real
  `pnpm install`, not a no-op. The pipeline ran **twice** under two different traceIds.
- `deploy.ts:83` `if (ctx.generatedArtifactsDir) return 'generator'` — and the deploy *was*
  the generator path (its `[deploy] WARNING: not copying review.Dockerfile…` lines are in the
  stream), so `generatedArtifactsDir` was set, so `buildStage` did call
  `buildMissingOutputs`. Yet no `[build] Built …` / `[build] Skipping …` line is in the stream.
- `stageBuildContext` is passed `stage.root`, and the guard reports exactly that path — so the
  deploy-stage guard is the one that fired, not the strategy's.

**Ruled out:** the tarball carrying a nested farm. `workspace.package()` excludes
`node_modules` bare and `./`-prefixed, which *looks* depth-blind, but BSD tar matches those by
basename at any depth — I verified with a probe tree that `services/platform-api/node_modules`
is dropped. The farm was not uploaded.

**Also ruled out:** the local worktree. Deleting `services/platform-api/node_modules` locally
changed nothing, because the upload excludes `node_modules` and the worker creates the farm.

Next step, if anyone picks this up: instrument the worker's `buildMissingOutputs` to log whether
it invokes `strategy.build()` for this app. Do **not** guess at a fix in
`packages/deploy-strategies` — that is shared deploy infrastructure for the whole federation.

### `apps.web` config warnings — investigated, deliberately NOT changed

Every deploy log carries, twice each:

```
[blueforge-config] blueforge.config.json: apps.web.role: Required
[blueforge-config] blueforge.config.json: apps.web.envs: every env must declare domains (directly or via extends)
```

`web` is `kind: "dev"` (E2E harness, documented as "must not reach production") and declares
neither `role` nor `envs`. `DeployUnitV2Schema` requires both.

**I did not silence it.** There is no precedent anywhere in the federation to copy — every
`kind: dev` app found is an lq-core worktree, all with `role=undefined envs=undefined`. The
`envs` refinement demands `domains` **or** `extends`, and inventing a domain for an app that
must never be routed is a real footgun, not a cosmetic risk. `role` is a free-form
`z.string()`, so a value could be chosen, but its consumers are unknown to me.

**The likely real fix is in forge-control, not here:** the schema's own comment acknowledges
`dev` apps ("a harness like lq-core's apps/web … must not reach production") yet still subjects
them to refinements that demand routable domains. Exempting `kind: 'dev'` from the `role` and
`envs` refinements would be consistent with that intent. Parked with the rest of the
forge-control work.

## 🐛 New forge-control defect found: deploy errors are truncated at 4000 chars

I could not diagnose class 2 because **the cause is not stored**:

```
2ba9a1ba  len=4000  ends '… resolution step is skipped #'
3a301ce6  len=4000  ends '[prebuild] generate-constants.ts absent '
```

`app_deploys.errorMessage` is capped at **exactly 4000 characters, keeping the HEAD**. A Docker
build log puts the error at the **END**. So every deploy that fails inside a `docker build` stores
4000 characters of *successful* build steps and discards the root cause.

The cap is invisible normally — short errors come through whole (`c926a377` is 2328 chars, and
those 25-symlink errors were fully legible). It only bites on build failures, which is exactly
when you need it.

**This is far more actionable than the parked dereference defect:** provable, reproducible, and a
small fix — keep the tail, or store full output separately and truncate only for display.

### Requested capability: don't prune what a build is using

The operator asked for a *smart* prune — reclaim only what no in-flight build is using. Agreed,
**with one sequencing caveat that matters: ship it in the same change as the under-prune fix.**

Today the over-prune risk is theoretical *because the job frees nothing*. The moment someone fixes
the `until=24h` filter so it actually reclaims 32 GB, the risk becomes real for the first time.
Fixing one without the other means shipping a job that suddenly deletes 32 GB underneath running
builds. Nothing suggests this job has broken a build — the defect is under-pruning, not
over-pruning.

Both guards are buildable from data that already exists:

1. **Queue guard (cheapest, strongest).** `forge builds queue status` is Redis-backed and live —
   measured `wait=0 active=2 failed=1717 completed=2093`, 1 worker, last seen 1s ago. Read
   `active` before pruning; skip or defer if non-zero. No new plumbing needed.
2. **Lease guard (per-build-session, already parsed).** `sweep_leases()` already extracts the
   `containerd.io/gc.flat=<RFC3339>` label to find *stale* leases. The same parse yields the
   *fresh* set — leases younger than a few minutes mean a build is mid-flight. More precise than
   the queue, because it is per build-session on that specific host.
3. **Dry-run blast radius.** `DRY_RUN` exists but never reports *what it would remove*. Add
   `docker image ls --filter dangling=true` + `docker system df -v` under dry-run.

**Caveat on `docker image prune -af`:** `-a` removes every image not referenced by a *container*. A
base image that an in-flight build pulled but that no container references looks unused to Docker.
BuildKit usually holds its own references, but the window between "pulled" and "referenced by a
build step" is real — which is exactly what guard 1 closes.

## ✅ FILED — forge-control#1758: disk telemetry reports the wrong filesystem

Asked whether the fleet exposes disk usage per host. **It does — and the number it reports is
about the wrong disk.** This is the first place the corrected measurements became load-bearing
rather than just a correction to my own notes.

Measured 2026-10-02 ~14:35Z over SSH, all five app hosts:

| host | `/` | `/var/lib/containerd` | `/var/lib/docker` |
|---|---|---|---|
| app-1 | `/dev/sda1` 75% | **`/dev/sda1` 75%** | `/dev/sdb` 5% |
| app-2 | `/dev/sda1` 85% | **`/dev/sda1` 85%** | `/dev/sdb` 4% |
| app-3 | `/dev/sda1` 84% | **`/dev/sdb` 50%** | `/dev/sdb` 50% |
| app-4 | `/dev/sda1` 6% | **`/dev/sdb` 22%** | `/dev/sdb` 22% |
| app-5 | `/dev/sda1` 74% | **`/dev/sda1` 74%** | `/dev/sdb` 2% |

Three findings:

1. **`/var/lib/docker` is a decoy.** All hosts run the containerd snapshotter
   (`docker info .Driver` = `overlayfs`), so images live in `/var/lib/containerd`.
   `DockerRootDir` still reports `/var/lib/docker`, which on 4 of 5 is a *different, near-empty*
   device. app-5's has **138 GB free** while the host is 74% full.
2. **No default path is correct fleet-wide.** containerd is on the same device as `/` on
   app-1/2/5 and a different one on app-3/4. Nothing transfers between hosts.
3. **`selectWorstMount` picks the *fullest* mount** — correct for prune, wrong for container
   pressure. On app-3 it selects `/dev/sda1` at 80.3% and raises `disk 80.3% ≥ 75%`, while the
   container store `/dev/sdb` is at 50% with **120 GB free**. The host is warning about a disk
   that cannot take a build, while the disk that would is half empty.

**Bonus bug found while verifying:** `GET /api/fleet/hosts/:slug/metrics/summary` reads `disk`
from `rows[0]` of a query with **no `orderBy`** (`host-metrics.ts:205-233`). app-5's summary
reported 84.6 GB against a live heartbeat of 105.6 GB — **21 GB stale**. Lines 91 and 150 of the
same file order correctly, so it reads as an oversight.

The four now-linked defects form one chain: a container-store problem is measured on the **wrong
machine** (`worker.ts` stats `BUILD_ROOT` locally), attributed to the **wrong host**
(`HOST_SLUG` = the worker), reported about the **wrong disk** (#1758), into a table **nothing
alerts from** (#1195). Cross-linked all four ways: #1758 ↔ #1754 ↔ #1195.

Two corrections to what I told the operator earlier, both from assuming a surface did not exist
before checking:

- "No API surface for host disk at all" — **wrong.** `GET /api/fleet/hosts/:slug/metrics` and
  `…/metrics/summary` both return disk; `forge host ls` has a `CAPACITY` column with `disk NN%`
  warn reasons. The surfaces exist. What is wrong is *which* filesystem they measure.
- `~/.forge-secrets/forge-admin-token` 401s against `api.blueforge.studio`. The control-plane
  key is `apiKey` in `~/.config/forge/credentials.json`. Filenames in `~/.forge-secrets/` are
