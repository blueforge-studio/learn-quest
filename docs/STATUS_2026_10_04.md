## The image-worker build failure — root cause and fix (MERGED ✅)

Chain, all verified:

1. `blueforge.config.ts` declared `workspaceDeps: ['packages/books-shared']` for
   `books-image-worker-api`, so forge-ops emits `RUN pnpm --filter @learnquest/books-shared build`
   in the per-app Dockerfile.
2. The worker's `package.json` has **never** declared books-shared (its only `@learnquest`
   mention is a comment), so the install filter `--filter @learnquest/books-image-worker-api…`
   never covers it → books-shared's devDep `tsup` is never installed → `sh: tsup: not found`.
3. The break started with the **pnpm@9 → pnpm@10 flip in `460d79b` (2026-09-08)**; the last good
   image was `2026-09-07T20:08Z`. The 10-02 session's "builds fine locally" was a
   warm-`node_modules` artifact.
4. Invisible for a month because `app_deploys.errorMessage` truncates at 4000 chars **keeping the
   HEAD** while docker build errors live at the tail (forge-control#1756 — now demonstrated by a
   month of lost diagnosis, not just theory).

**Fix:** the worker imports nothing from the workspace, so the phantom `workspaceDeps` is dropped
outright; auto-derive emits a clean Dockerfile with no books-shared steps.

- PR **books-platform#48** (branch `fix/image-worker-workspace-deps`, squash → main `794422ab`),
  CI green (`ci / check`, `Sidecars`, `Symlink guard` all ✅), merged with `fgit pr merge` — no
  force needed.
- Validated **before** the PR: exact Dockerfile build on app-1 from the staged context
  `/opt/books-platform/books-image-worker-api/` (which is a full monorepo staging; compose runs
  it with the per-app `.override.yml`). Full build passed, container booted, `/api/health` 200,
  fail-closed 503 without `INTERNAL_API_KEY` preserved. Repro tags removed after.

## The `.env` regen trap, second bite (method note)

The first CI run on #48 went red at `generate-dockerfiles --check` on two **unrelated**
`blueforge.json` files (books-api `S3_*`, lq-book-marketplace `VITE_USE_POSTGRES`). Cause: the
generator's `parseEnvFiles` reads gitignored `<app>/.env`, so a regen on the working checkout
bakes local-only vars into the committed artifacts; CI (clean checkout) derives less and reports
drift. Both apps' `.env` files exist locally and carry exactly those vars.

**Clean-room technique that settles it:** fresh clone + `pnpm install --frozen-lockfile` + run the
check — reproduces CI's derivation exactly (clone kept at `~/tmp-books-cleanroom` as a control;
the local `next build` passes there, which matters for the books-site item below). The committed
artifacts were reverted to main's versions and the branch amended.

> Never trust a local `--check` green on the working checkout alone. Regenerate for commit from a
> clean room, or move the `.env` files aside first. Both failure directions have now happened.

## 🐛 New blocker: books-platform webhook deploys fail at lq-books-site (forge-control side)

The merge of #48 triggered the normal webhook deploy `686e6ded` (commit `794422ab`). It died in
the build-worker's build stage:

```
build failed for app 'lq-books-site' (next): Command failed: pnpm --filter '@learnquest/books-site...' build
Error: Turbopack build failed with 42 errors:
  Module not found: Can't resolve '@vercel/turbopack-next/internal/font/google/font'
  next/font/google queries have exactly one entry
  (all in [next]/internal/font/google/inter_ba811ce.module.css, from src/app/layout.tsx)
```

Constraints established:

- **Not egress:** `fonts.googleapis.com` and `registry.npmjs.org` both reachable from inside the
  worker container.
- **Not the repo:** the identical build passes locally (clean room, macOS) — books-shared's tsup
  **succeeded** in the worker too; the failure is purely the Turbopack font module.
- **Not pre-existing code:** the worker build stage passed for all apps on 2026-10-01 and
  2026-10-02 (those deploys reached the migration / host-build stages).
- **The correlate:** the forge-build-worker image was rolled **2026-10-04 16:13:44Z** to
  `build-worker:f767def8…` — the failed deploy at 16:29 was its first books-platform build. The
  worker provides node/corepack to the build; a toolchain bump is the prime suspect.

Full log recovered from `docker logs forge-build-worker` on ci-1 (the deploy record is again
head-truncated at 4000 — #1756 bites on the pipeline path too, not just the host path; and the
worker's own stdout is the only complete copy of a build log that exists anywhere).

**Fix belongs in forge-control** (identify what changed in `f767def8`'s worker — likely node
version — and either pin back or fix the worker env) **or books-platform** (switch lq-books-site
to `next/font/local` to make the build hermetic and worker-proof). Until then, per-app deploys
(`forge app-deploy <app> --server --no-dns`) are the workaround; project webhook deploys of
books-platform will fail.
