## The image-worker build failure — root cause and fix (MERGED ✅)

Chain, all verified:

1. `blueforge.config.ts` declared `workspaceDeps: ['packages/books-shared']` for
   `books-image-worker-api`, so forge-ops emits `RUN pnpm --filter @learnquest/books-shared build`
   in the per-app Dockerfile.
2. The worker's `package.json` has **never** declared books-shared (its only `@learnquest`
   mention is a comment), so the install filter `--filter @learnquest/books-image-worker-api…`
   never covers it → books-shared's devDep `tsup` is never installed → `sh: tsup: not found`.
3. The break started with the **pnpm@9 → pnpm@10 flip in `460d79b` (2026-09-08)**; the last good
   image was `2026-09-07T20:08Z`. The 10-02 session's "builds fine locally" was a
   warm-`node_modules` artifact.
4. Invisible for a month because `app_deploys.errorMessage` truncates at 4000 chars **keeping the
   HEAD** while docker build errors live at the tail (forge-control#1756 — now demonstrated by a
   month of lost diagnosis, not just theory).

**Fix:** the worker imports nothing from the workspace, so the phantom `workspaceDeps` is dropped
outright; auto-derive emits a clean Dockerfile with no books-shared steps.

- PR **books-platform#48** (branch `fix/image-worker-workspace-deps`, squash → main `794422ab`),
  CI green (`ci / check`, `Sidecars`, `Symlink guard` all ✅), merged with `fgit pr merge` — no
  force needed.
- Validated **before** the PR: exact Dockerfile build on app-1 from the staged context
  `/opt/books-platform/books-image-worker-api/` (which is a full monorepo staging; compose runs
  it with the per-app `.override.yml`). Full build passed, container booted, `/api/health` 200,
  fail-closed 503 without `INTERNAL_API_KEY` preserved. Repro tags removed after.

## The `.env` regen trap, second bite (method note)

The first CI run on #48 went red at `generate-dockerfiles --check` on two **unrelated**
`blueforge.json` files (books-api `S3_*`, lq-book-marketplace `VITE_USE_POSTGRES`). Cause: the
generator's `parseEnvFiles` reads gitignored `<app>/.env`, so a regen on the working checkout
bakes local-only vars into the committed artifacts; CI (clean checkout) derives less and reports
drift. Both apps' `.env` files exist locally and carry exactly those vars.

**Clean-room technique that settles it:** fresh clone + `pnpm install --frozen-lockfile` + run the
check — reproduces CI's derivation exactly (clone kept at `~/tmp-books-cleanroom` as a control;
the local `next build` passes there, which matters for the books-site item below). The committed
artifacts were reverted to main's versions and the branch amended.

> Never trust a local `--check` green on the working checkout alone. Regenerate for commit from a
> clean room, or move the `.env` files aside first. Both failure directions have now happened.

# Addendum (same day, evening): all three next steps executed

## 1. Worker-roll investigation — correlation dissolved, real cause found and fixed

- `f767def8` itself is autoscaler-only; the worker Dockerfile (node:22-alpine + corepack pnpm@10)
  is unchanged since 10-01, and the 10-03 and 10-04 worker images have **identical** toolchains
  (node v22.23.3, corepack 0.36.0, pnpm 10.26.1). The "worker-roll regression" framing was wrong.
- The decisive experiment: cloned the repo **inside the worker container** and ran the exact
  `pnpm --filter '@learnquest/books-site...' build` — **fails there deterministically** on the
  merge commit, passes on macOS. With toolchains identical, the one floating input left is the
  **css2 response Google serves at build time** — `next/font/google` fetches it on every build and
  Turbopack's font-module mapping chokes on a response shape it didn't expect. (Worker builds
  passed 10-01/02 and fail now with no code change: that's the signature of a remote-response
  change, not an environment change.)
- **Fix (books-platform#49, MERGED ✅):** `next/font/local` with a committed InterVariable.woff2
  (SIL OFL 1.1, license beside the font + THIRD_PARTY_LICENSES.md). Hermetic: no build-time fetch,
  no Turbopack font module. `--font-inter` unchanged. **Verified inside the failing container**:
  the same in-worker repro that failed with 42 errors passes with the committed font.

## 2. Second blocker underneath: the audio-storage image closure (#50, MERGED ✅)

With the font fix in, the next full deploy progressed past the worker build stage and failed in
the **host-side** image build of `lq-books-site` — head-truncated again; the untruncated error
came from re-running the exact Dockerfile build on app-1:

```
TS2307: Cannot find module '@learnquest/audio-storage'
  (from packages/books-reader/src/{components/NarrationControls,hooks/useAudioNarrationUrl})
```

- books-reader imports it; **audio-storage exports are dist-only** (no source condition — unlike
  books-reader, whose exports point at `./src/*.ts`, which is why SPAs never needed dep dists);
- the Dockerfile copies only `workspaceDeps`, which were listed one level short;
- the worker build stage never catches this (full clone, every package present) — only the image
  build, which sees exactly what the Dockerfile copies.

**Fix (#50):** declare `@learnquest/audio-storage: workspace:*` in books-site + interactive-book
(the audit's one undeclared-import finding), add `packages/audio-storage` to both `workspaceDeps`,
regenerate. The dist comes from the staged context, which the worker build stage populates — the
same reliance every SPA already has on its books-shared dist. A transitive-closure + dep-build
fix belongs in the forge-ops generator templates (frontend-next/frontend-vite) and was
deliberately **not** attempted — shared federation infra.

Validated on app-1: both images build; books-site serves `/` → 200, correct title. CI green; both
PRs merged without force.
