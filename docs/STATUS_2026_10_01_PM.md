## New blocker found and fixed — books-platform build (PR #43, merged)

With assetSync green, the deploy advanced and failed one phase later, at the image
build. This is a **new** failure, not a continuation — it was masked by the bucket bug.

```
> @learnquest/books-shared@0.1.0 prebuild: `tsx ../../scripts/generate-constants.ts`
ERR_MODULE_NOT_FOUND  url='file:///app/scripts/generate-constants.ts'
```

`packages/books-shared` has a `prebuild` that regenerates
`src/schemas/__generated__/bookGenres.ts` from `data/config/book-genres/en.json`. The
generated Dockerfiles copy **only `packages/`** — no `scripts/`, no `data/` — so the
hook points at a file that isn't in the build context. Hits all three backend images
that build books-shared: **books-api, stripe-api, books-image-worker**.

The fix is in the hook, not the Dockerfile: `apps/*/Dockerfile` is a derived artifact
of `blueforge.config.ts` and the forge-ops generator has no extra-COPY concept, so
hand-editing it would fail the `generate-dockerfiles --check` gate. The guard keys off
file *absence* only, so a genuine generator failure still fails the build loudly rather
than silently shipping stale constants.

Skipping regeneration does make a stale generated file invisible to the image build, so
PR #43 also adds the `generate-constants:check` CI gate to `.gitea/workflows/ci.yml`.
**Nothing enforced that before**, so a stale constants file could already have shipped.
**Merged as `405e068`.**

/app/apps/books-api/drizzle.config.ts     -> absent
/app/node_modules/.bin                    -> no drizzle-kit

The conclusion is unchanged and is now evidence rather than inference: the step cannot
run, for **two independent reasons** — the `cwd`, and the missing `drizzle/` folder,
`drizzle.config.ts` and drizzle-kit binary. Fixing the cwd alone would have **moved** the
failure rather than removed it. The `migrations` block was removed (PR #45) rather than
half-fixed, matching the federation convention that migrations do not apply at boot.

Lesson worth keeping: I inferred the failing SQL from a *reproduction* of a symptom I
could reproduce locally, not from the deploy's actual output. The deploy's real error was
available all along in `forge status`.

The block is now removed (PR #45) rather than half-fixed — making deploy-time migrations
work is a change to `deploy/Dockerfile.api`, not to the config. This also matches the
federation convention that **migrations do not apply at boot**.

### How drizzle decides to skip — the actual predicate

Before writing anything I read the installed code rather than assuming. In
`drizzle-orm@0.42.0` `pg-core/dialect.cjs`, `PgDialect.migrate()` does:

```js
const dbMigrations = await session.all(
  sql`select id, hash, created_at from "drizzle"."__drizzle_migrations" order by created_at desc limit 1`);
const lastDbMigration = dbMigrations[0];
…
if (!lastDbMigration || Number(lastDbMigration.created_at) < migration.folderMillis) { /* apply */ }
```

Three consequences that make the baseline safe:

1. It reads **one** row — the highest `created_at` — and compares it to **every** migration.
   So a single baseline row is sufficient; no need to backfill the whole journal.
2. **`hash` is never compared.** It is written but only used for the audit trail.
3. `folderMillis` is the journal's `when` (`readMigrationFiles()` in `migrator.cjs`).

With one row at `created_at = 1788675743058`:

```
0000_overjoyed_marvel_zombies: 1788675743058 < 1788675743058  -> false -> SKIP
0001_lame_timeslip:            1788675743058 < 1789211908570  -> true  -> APPLY
```

The bookkeeping DDL is likewise fixed and was reproduced verbatim:
`CREATE SCHEMA IF NOT EXISTS "drizzle"` and
`CREATE TABLE IF NOT EXISTS "drizzle"."__drizzle_migrations" (id SERIAL PRIMARY KEY, hash text NOT NULL, created_at bigint)`.

### Two gotchas hit on the way

- **The running 09-11 image ships no `drizzle/` folder and no `drizzle-kit`.** Migrations
  are *new* to this deploy, which is why the step only started failing now.
- **`forge app-deploy books-platform` is the wrong invocation.** `books-platform` is the
  **project** name (`blueforge.config.ts:154`); the CLI wants an **app** name from the
  config's `apps` block. It fails with `--app books-platform not found or not deployable
  in apps:` — and **exits 0 while printing `✗ Server deploy failed`**. The correct call is
  `forge app-deploy books-api --server`, since the migration config is on that app.
  The registry does pin placement to app-1 even without a `server` field in the config.
- **`psql` inside `postgres-shared` never checks the password.** Its `pg_hba.conf` has
  `trust` for `local` and `127.0.0.1/32`, and `scram-sha-256` only for everything else.
  So any query run with `docker exec postgres-shared psql …` succeeding tells you nothing
  about whether the credentials work — the password is never exercised. The password in
  `DATABASE_URL` **is** valid: it authenticates over TCP from a sibling container. Reach
  the DB from the docker network (e.g. from `books-api`, which has `pg`), not over an
  SSH tunnel — a tunnel to the container IP failed auth, and the role also has
  `rolcreatedb = f`, so it cannot create the scratch database a tunnel-based rehearsal
  would need.
