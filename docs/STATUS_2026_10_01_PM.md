## New blocker found and fixed — books-platform build (PR #43)

With assetSync green, the deploy advanced and failed one phase later, at the image
build. This is a **new** failure, not a continuation — it was masked by the bucket bug.

```
> @learnquest/books-shared@0.1.0 prebuild: `tsx ../../scripts/generate-constants.ts`
ERR_MODULE_NOT_FOUND  url='file:///app/scripts/generate-constants.ts'
```

`packages/books-shared` has a `prebuild` that regenerates
`src/schemas/__generated__/bookGenres.ts` from `data/config/book-genres/en.json`. The
generated Dockerfiles copy **only `packages/`** — no `scripts/`, no `data/` — so the
hook points at a file that isn't in the build context. Hits all three backend images
that build books-shared: **books-api, stripe-api, books-image-worker**.

The fix is in the hook, not the Dockerfile: `apps/*/Dockerfile` is a derived artifact
of `blueforge.config.ts` and the forge-ops generator has no extra-COPY concept, so
hand-editing it would fail the `generate-dockerfiles --check` gate. The guard keys off
file *absence* only, so a genuine generator failure still fails the build loudly rather
than silently shipping stale constants.

Skipping regeneration does make a stale generated file invisible to the image build, so
PR #43 also adds the `generate-constants:check` CI gate to `.gitea/workflows/ci.yml`.
**Nothing enforced that before**, so a stale constants file could already have shipped.
The committed output is currently up to date.

**Not yet merged or deployed** — CI had not reported at time of writing. books-platform
still runs 09-11-era images; PR #37 (cover art) stays behind it.

## Found, not fixed — `STORAGE_PROVIDER=r2` is an invalid value

This is the "needs R2 env" blocker behind the lazy-asset pilot, and it is a **typo, not
a missing credential**:

```
[lazy-asset] disabled — storage provider r2 could not be initialised:
  Unknown STORAGE_PROVIDER: "r2".
  Supported values: backblaze_b2, cloudflare_r2, minio, supabase, generic_s3, memory
```

`IMAGE_LAZY_GENERATION_ENABLED=true` is set correctly, but `STORAGE_PROVIDER=r2` is not
an accepted value — the service wants **`cloudflare_r2`**. Storage init is wrapped in a
try/catch that logs this and continues, so platform-api stays **healthy and serves every
other route** while the lazy-asset router is simply never mounted. That is why it is
easy to miss: the 404 looks like a routing bug, and `/api/assets/lazy` is absent from
the `/api/health` route list rather than erroring.

Prod state: `learnquest-core` container healthy on app-3, up 4h (matches deploy
`362727eb`), 0 restarts. `forge app list` reports `failed/errored` — that flag is stale,
the app is serving. **Fix:** `forge env set learnquest-core STORAGE_PROVIDER cloudflare_r2`,
then redeploy. Note the R2 account-ID gotcha still applies
(`project_books_platform_r2_account_id.md`).

app-3 is over its capacity warning threshold (disk 80.5%, 19 apps placed vs warn at 15).
